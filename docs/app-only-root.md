# アプリ単独での初回 root：実測した結果と、成立しない理由

`charepa-apk` の v1.0.0 は**adb か画面からの 1 コマンド**を前提にしている。初回 root は
`run-as`（shell 文脈、`CapBnd = 0xc0`）で走らせ、2 回目以降はアプリ自身が
`/proc/myroot` を叩く。この文書は「アプリだけで、素の端末から root を取れるか」を
実機で測った記録である。

結論は**成立しない**。理由は 1 つではなく、機構の各段で判明した。

## 前提: 錨になる語が要る

チェーンの初回 root は、`/dev/ion` の `ION_IOC_PHYS` を「テスト兼書き込み」に使う。
この ioctl は `arg` をカーネルポインタとして読み、`*(u32*)arg` を fd 番号として解釈する。

- その番号の fd が dma-buf でなければ、何も書かずに `-1`
- dma-buf なら、その IOVA を `arg+4` に書く

つまり「ある 4 バイトが、いま開いている fd 番号と一致する」場所を探す必要がある。
シェル文脈では `cap_bset.cap[0] = 192`（`0xc0`）がその役を果たす。fd 192 に dma-buf を
置けば、192 という語を持つ構造体だけがゲートを通る。

**アプリ文脈（`untrusted_app`）では `CapBnd = 0000000000000000`** なので、この語は無い。

## 測った代替の錨と、その結果

`cred->usage`（+0）は、その cred を共有するタスク数である。アプリでも値を動かせるので
錨の候補になる。実測はこうなった。

| 仕掛け | 錨の値 | fd | 結果 |
| --- | --- | --- | --- |
| 単一スレッド | 1 | 1 | 当たらない（全 RAM、stores 20） |
| 191 スレッド | 192 | 192 | 候補 1576、うち 485 が +52 を通る、自分の cred は含まれず |
| 95 スレッド | 96 | 96 | 候補 810、当たらず |
| 191 スレッド + オフセット +1/-1 | 193/191 | 193/191 | 当たらず |

`gate(o+0)` が通れば `o+4`（uid）に IOVA が入るので、自分の cred に当たったかどうかは
`getuid()` の変化で分かる。どの条件でも `getuid()` は変わらなかった。つまり
**usage の錨は、自分の cred に一度も届いていない**。

`approot7`（アプリ文脈、全 RAM）の実測:

```
Threads=192 guard word 192 (offset 0)
guard on fd 192, iova 0x800c0000
uid before phase A = 10044 (0x0000273c)
phase A probes=10838016 stores=1525 candidates=1525
uid after phase A = 10044 (unchanged: our cred was NOT among the matches)
```

## 第 2 段も成立しない

錨が当たったとしても、次の段で止まる。

`grant_avc` は fd 4 だけに dma-buf を残し、「通った＝クラス 4」と厳密に判定する。
アプリ文脈では、`cred+52`（`cap_permitted.cap[1]`）を叩くために fd 0 を dma-buf に
する必要がある。ところが**アプリのプロセスは fd 0 を含めて十数個の fd を既に開いている**
（binder、ashmem、APK、自分のファイル）。実測では 485 個の候補が +52 のゲートを通った。
これは「+52 の語が 0 だった」のではなく「+52 の語がどれかの fd 番号だった」という意味で、
書き込み先は cred ではない構造体に散る。

シェル経路が安全なのは、fd 4 以外の dma-buf を全部閉じてから絞り込むからである。
アプリ文脈では、その「他」に当たる fd を自分で閉じられない。

## 測った範囲と、測れていないこと

実測は TAB-A03-BR2（`0C8R236091`、`3.10.33 #2`）で行った。容器はすべて
`charepa-apk/tools/app-root/` に置いてある。

- `approot1.c` — `cred->usage` を錨にし、uid の変化で自分の cred を検出する
- `approot3.c` — 191 スレッドで usage を 192 にし、fd 192 に IOVA 0x800C0000 を置く
- `approot5.c` — 候補を集めて 1 つずつ cap_effective を試す（charepa と同じ形）
- `approot7.c` — 自分の cred が候補に入ったかを uid の変化で判定する

測れていないのは次の点である。

- `cred->usage` の実際の値（`Threads` と一致しないことは分かったが、真の値は未測定。
  自分で root を取ってから測る方法を試したが、`re_root()` が cred を差し替えるため
  測りたい cred が消える）
- `struct cred` の実サイズ（192 バイト格子で歩いたが、128 バイト格子・64 バイト格子でも
  当たらなかった。配置の仮定そのものが未確認）
- 日本語版 BR2 での挙動

## 実務的な結論

**素の端末で、adb も USB も使わずにアプリだけで root を取る経路は、この端末では
成立しない。** 根拠は上に書いた 2 点で、どちらも実測による。

現実的な選択肢は次の 3 つで、いずれも「初回だけ外部から 1 回」を要する。

1. `adb shell run-as com.charepa <path>/charepa all` を 1 回（v1.0.0 の現行手順）
2. 端末の画面でアプリを開き「all」を押す（初回 root はシェル文脈でしか通らないため不可）
3. 既に root 化済みの個体に APK を入れ、`/proc/myroot` 経由で 2 回目以降を維持する
   （BS・BR2 の両方で実測済み）

2 が不可なのは、初回 root の錨が `CapBnd = 0xc0` に依存し、アプリの `CapBnd` が 0 だから
である。これは回避できない（アプリが自分の `CapBnd` を変える手段が無い）。
